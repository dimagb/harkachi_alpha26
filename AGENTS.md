Проект — прототип «Умный кредитный кабинет предпринимателя» (хакатон «Альфа-Будущее 2026»). Сдача 26.10 в 18:00, заморозка в 12:00. Жюри поднимает проект одной командой `docker compose up` на чистом Windows-ПК и проверяет по README. Тимлид — Claude: он владеет контрактами, раздаёт задачи и сливает PR. Твой оператор — человек, который не программирует: пиши ему коротко и по-русски.

## 1. Источники правды (в порядке силы)
1. `contracts/` — это закон, менять его нельзя:
   - `api-types.ts` — типы API;
   - `api.md` — пути, роли и переходы;
   - `codes.md` — все перечисления и коды;
   - `external-mocks.md` — внешние источники;
   - `personas.json` — данные демо-персонажей и ожидаемые исходы;
   - `decision_reference.py` — эталон модели решения.
2. Карточка твоей задачи в `docs/TASKS.md`: что делать, какие файлы трогать, как принимается работа.
3. `docs/` — модель процесса (`process.md`, `state-machine.md`, `decision-model.md`, `data-model.md`, `architecture.md`, `screens.md`). Читай только разделы, указанные в карточке.

Если карточка расходится с `contracts/`, прав `contracts/`. Расхождение опиши в PR.

## 3. Порядок работы над задачей
1. `git status`: рабочая копия должна быть чистой. Если в ней остались изменения от прошлой задачи, **ничего не удаляй и не переноси**: остановись и сообщи оператору (`notify.py BLOCKER <ID> "незакоммиченные изменения"`). В одной папке одновременно работает только один агент; для второй задачи нужна вторая копия репозитория.
2. `git switch main && git pull --ff-only`, затем `git switch -c <роль>/<ID>-<коротко>` (например, `backend/B-02-decide`). Новая ветка всегда создаётся от свежего `main`. Проверь: `git log -1 --oneline origin/main` совпадает с `git log -1 --oneline main`.
3. Уведоми о старте: `uv run --no-project python tools/notify.py START <ID> "<что начал>"`.
4. Работай маленькими коммитами. Сообщение коммита: `<ID>: что сделано`.
5. Сначала тест, потом код (скилл `test-driven-development`, если установлен). Каждое требование карточки покрыто тестом или командой проверки.
6. Перед PR подтяни свежий `main`: `git fetch origin && git rebase origin/main`. Если в `contracts/openapi.json` или `frontend/src/api/schema.d.ts` есть конфликт, не правь его руками: возьми версию из `main` и перегенерируй файл скриптом (§2). Конфликт в чужом файле — блокер. После rebase выполни **все** команды из раздела «Приёмка» карточки, а также линтеры и тесты своей папки. Вывод вставь в PR.
7. `git push -u origin <ветка>` (после rebase в **свою** ветку допустим `git push --force-with-lease`), затем `gh pr create --base main --title "<ID>: <название>"`. Тело PR — по шаблону из §6.
8. Если CI красный — чини, но не дольше 60 минут. Потом остановись и опиши в PR, что падает.
8а. **Самопроверка перед DONE.** Выполни `/review` своей ветки против `main` (встроенное ревью Codex), сверь каждое замечание с карточкой и `contracts/`, исправь найденное в той же ветке и повтори приёмку. В PR добавь раздел «Самопроверка»: что нашёл `/review` и что исправлено или почему не исправлено.
9. Уведоми: `uv run --no-project python tools/notify.py DONE <ID> "PR #<номер>, CI зелёный"`.
10. **Не сливай PR сам.** Сливает тимлид или человек после ревью. Замечания ревью исправляй в **той же ветке**, даже в новом чате: `git switch <ветка PR> && git pull`, новую ветку не создавай (скилл `gh-address-comments`).

**Codex Cloud с 25.10 не используем (D20): ты работаешь на ноутбуке оператора.** Абзац ниже — для истории.
В **Codex Cloud** нет `gh` и токена бота. Ветку и PR создаёт сама кнопка «Create PR», а `notify.py` в облаке не вызывается: о результате сообщает оператор. Docker и Postgres в облаке недоступны, поэтому туда отдаются только задачи с пометкой «Облако: да». **Доступа к GitHub из облака нет** (`git fetch`, `pull`, `push` падают с ошибкой прокси — это нормально): шаги 1–2 и 5–7 §3 в облаке пропускаются, код уже взят с ветки, выбранной при запуске. Если нужен свежий `main` — оператор запускает новую задачу облака, а не просит агента обновиться.

## 4. Вопросы и блокеры
- **Неблокирующий вопрос** (можно продолжать):
  1. выбери самое осторожное толкование контракта, то есть то, которое легче всего поменять потом;
  2. отметь место в коде комментарием `# TODO(lead): <вопрос>` (или `// TODO(lead)`);
  3. впиши вопрос в раздел «Допущения и вопросы» PR;
  4. отправь `notify.py QUESTION <ID> "<вопрос в одну строку>"`;
  5. продолжай работу.
- **Блокер** (без ответа задачу не продолжить): `notify.py BLOCKER <ID> "<что именно мешает>"`, затем черновой PR с описанием. Останавливайся целиком, только если блокируется **вся** задача. Если проблема касается одного пункта, сделай всё остальное.
- Не придумывай обходы контрактов, не добавляй поля, коды и эндпоинты, которых нет в `contracts/`.

## 5. Правила кода (нарушение — PR не сливается)
- **Деньги** — целые рубли (`int`, в БД `bigint`), без `float` в суммах. Платёж округляется до рубля по ROUND_HALF_UP, сумма встречного — вниз до 50 000. **Ставки** — 2 знака. **Даты** — ISO 8601, моменты времени в UTC.
- **Pydantic v2:** у каждой схемы запроса и ответа `model_config = ConfigDict(extra="forbid")`. Названия классов и полей совпадают с `api-types.ts`.
- **Внутренние данные никогда не попадают в клиентский API:**
  - `risk_flag`, `internal_reasons`, `factors`, `rules_fired`, `inputs_snapshot`, пороги, код `SF_ADDITIONAL`;
  - для клиента и для банка — разные классы ответа, а не один класс с условной выдачей полей.
- **Перечисления** берутся только из `contracts/codes.md`. Новых кодов не придумывай.
- **Ошибки** — только в формате `ApiError` с кодами из `api-types.ts`.
- **Тексты для пользователя** — на русском, понятные человеку без банковского опыта, без внутренних кодов.
- **Зависимости.** Новую библиотеку добавляй, только если она нужна по карточке. Укажи её в PR (название, версия, лицензия: нужна для `THIRD_PARTY_NOTICES`). Платные сервисы, ключи API, LLM и внешние сети запрещены (ограничения кейса: автономность и бесплатность).
- **Тесты нельзя ослаблять, чтобы CI стал зелёным.** Запрещено:
  - удалять или пропускать тесты, ставить `skip` или `xfail` без `TODO(lead)` и объяснения в PR;
  - снижать требования линтера;
  - менять ожидаемые значения golden-тестов (`personas.json`);
  - отключать проверки CI;
  - ставить `# noqa`, `# type: ignore`, `eslint-disable`, `@ts-ignore`, `any` без `TODO(lead)` и объяснения в PR.
- **Секреты** и `.env`, `.notify.env` не коммитятся. В репозитории — только `.env.example`.
- **Переносы строк** — LF (задано в `.gitattributes`). Shell-скрипты для Docker пиши без CRLF.
- **Опасные команды запрещены:**
  - `git push --force` в чужие ветки и в `main`;
  - прямые коммиты в `main`;
  - `git reset --hard` на чужих изменениях;
  - удаление файлов вне задачи.

## 6. Шаблон тела PR
```
## Что сделано
<пункты карточки → где сделано>
## Изменённые файлы
<вывод git diff --stat origin/main...HEAD>
Файлы вне карточки: нет / <список и причина>
## Приёмка
| Пункт приёмки | Тест или команда (file::name) | Итоговая строка вывода |
| --- | --- | --- |
## Полный итог тестов
<последние строки pytest -q -rA или npm test: passed / failed / skipped / xfail; skipped и xfail = 0 или объяснены>
## Проверка на обходы
<вывод: git diff origin/main...HEAD | grep -nE "skip|xfail|noqa|type: ignore|eslint-disable|ts-ignore|: any\b" — или «пусто»>
## Не выполнено (для облака и при лимите)
<пункты приёмки, которые не запускались, и почему; «нет»>
## Отклонения от карточки
<что и почему; «нет», если нет>
## Допущения и вопросы
<TODO(lead): …; «нет», если нет>
## Самопроверка
<что нашёл /review → что исправлено или почему нет>

## Новые зависимости
<название, версия, лицензия; «нет»>
```

## 7. Экономия лимита (Plus: окно 5 часов и недельный лимит)
- Читай только файлы и разделы из карточки. Не обходи весь репозиторий.
- Документацию библиотек смотри через MCP `context7`, если он подключён, иначе — официальную документацию. Не пиши по памяти, особенно для Mantine 9.
- Если лимит кончается, закоммить сделанное, открой черновой PR с описанием «что осталось» и отправь `notify.py BLOCKER <ID> "лимит"`.

## 8. Команды по умолчанию
- Бэкенд и моки (из своей папки):
  - `uv sync`;
  - `uv run ruff check .`;
  - `uv run ruff format --check .`;
  - `uv run pytest -q`.
- Фронтенд: `npm ci`, `npm run lint`, `npm run typecheck`, `npm test`, `npm run build`.
- Стенд целиком: `docker compose up -d --build --wait`, `docker compose ps -a`, `docker compose logs <сервис> --tail 50`, `docker compose down -v`.
- Эталон решения: `uv run --no-project python -X utf8 contracts/decision_reference.py`.
