Окно разработки: 24.10 (сб) — 26.10 (пн) 12:00, около 2,5 дня. Катя недоступна 25.10 (вс). Код пишут агенты Codex, люди — операторы. Ведущий — тимлид, дизайн и интеграция.

## 1. Рамка: что должно быть правдой в демо

Жюри само заходит под клиентом и создаёт **новую** заявку. За 10–15 минут оно видит один из четырёх исходов (одобрение, встречное, дозапрос, отказ) с понятным «почему». Доводит одобренную заявку до «Выдано». Видит, что происходило с заявкой на стороне банка. Всё поднимается одной командой `docker compose up`.

## 3. Фишки человека — MoSCoW

| Идея | Приоритет | Почему |
| --- | --- | --- |
| Объяснение решения (два уровня) | **Must** | Q37, главное отличие, дёшево при правилах |
| Лента прогресса | **Must** | Это не фишка, а требование (F16, F19, F24) |
| Автозаполнение по ИНН (моки) | **Must** | Кейс: «сокращать повторный ввод» |
| Предрасчёт «узнать доступную сумму» | Could → доработка | Норма рынка (JTBD 2), но это второй путь скоринга без БКИ. На отбор хватит калькулятора платежа в форме заявки |
| Подсказки по интерфейсу | Входит в Must F24 | Не отдельная фишка: «что происходит / что дальше» на каждом экране |
| Светофор здоровья бизнеса | Could | Риск «научить обходу скоринга»; без него можно обойтись |
| Зонтичное поручительство | Could → доработка | Имеет смысл с крупными суммами и залогом |
| Сканер льготных программ | Could → доработка | Можно одну программу «КС + 3» как продукт каталога |
| Симулятор «кредит / субсидия / грант» | Won't (сейчас) | Уводит от конвейера (W2-Q14) |
| LLM-ассистент, OCR документов | Won't (сейчас) | Q19, Q47: баллов не даёт; риск запуска на проверке |

**Ядро во всех вариантах (Must, не забыть):** сохранение данных и статуса (F6); машина состояний отклоняет недопустимый переход (F19); ставка = ключевая ставка (параметр с датой) + спред − скидки (F20); слой политики причин; журнал аудита со снимком данных на момент решения.

**Скоринг (общий для всех вариантов) [М, уверенность высокая]:** балльная модель на правилах + отдельная кредитная политика. ML и LLM в MVP нет. Основание: кейс с. 14, Q19, Q27, Q37, Q47; пороги банки не публикуют; объяснимость нужна по закону (ИП) и Q37. ML-заглушку можно описать как развитие.

## 4. Три варианта

### Вариант A — «Автоконвейер + прозрачный журнал»
Ядро Must без ручного шага. Банк представлен экраном «Заявки банка» только для чтения: список, карточка, журнал этапов и факторов. Решает только автомат; дозапрос — автоматически при неполных или противоречивых данных.
- **Покрытие:** все Must из чек-листа, кроме F18 (человек — только в описании).
- **Плюсы:** самый быстрый, меньше всего интеграционного риска.
- **Минусы:** банковская сторона — витрина, а не процесс. Критерий 3 (UX банка) и Q10 (где человек) слабые. Жюри от банка может счесть это «калькулятором».
- **Оценка:** ~60% мощности команды; запас на отладку и Docker.

### Вариант B — «Автомат + андеррайтер для исключений» (рекомендую)
A + рабочее место андеррайтера в том же веб-интерфейсе (роль «Сотрудник банка»): очередь заявок на ручное рассмотрение, карточка с данными, факторами и рекомендацией системы, решение с комментарием. Плюс поручитель-учредитель для ООО (отдельная учётка, согласие и подпись). Плюс предрасчёт и статические подсказки (Should — режем первыми).
- **Покрытие:** все Must + F18 + F14a; правдоподобие для банка (поручитель, ручной шаг).
- **Плюсы:** закрывает обе стороны процесса (Q4, Q10, критерий 3); демо-сценарий «автоодобрение» и «пограничная → андеррайтер» показывает зрелость; один интерфейс с ролями — по уточнению организаторов.
- **Минусы:** больше состояний (очередь, возврат на дозапрос) и экранов; нужна дисциплина контрактов.
- **Оценка:** ~85–90% мощности. Предрасчёт и подсказки — буфер: режем, если к 25.10 вечером ядро не прошло E2E.

### Вариант B-lite — «A + андеррайтер для исключений» (рекомендую после critic)
A + рабочее место андеррайтера (роль в том же интерфейсе): очередь заявок по правилу (пограничный скор, сумма выше порога, возражение ИП), карточка с данными и рекомендацией системы, решение с комментарием. Поручитель — в той же сессии (директор = единственный учредитель), без второй учётки. **Без** предрасчёта и отдельных подсказок.
- **Покрытие:** все Must + F18 + F14a + возражение ИП.
- **Почему лучше B:** убирает два самых дорогих куска B (вторая учётка поручителя, второй путь скоринга) и оставляет всё, что даёт баллы.
- **Оценка:** функции ~60–65% + блок T ~25–30% (см. §7) = ~90%. Это честная цифра, запас небольшой.

### Вариант C — «Полное рабочее место + фишки»
B + несколько банковских ролей (менеджер, андеррайтер, СБ, комитет), зонтичное поручительство, светофор, LLM-подсказки, загрузка документов.
- **Плюсы:** выглядит богато.
- **Минусы:** ~150% мощности — не успеем; Q11: «проработанная основа важнее множества функций». Высокий риск сломать основной путь.
- **Оценка:** не рекомендую на отбор; часть — в доработку 17–27.11.

## 6. Детерминированное демо (вход для этапа 3 и README)

Жюри должно получить каждый исход само, по README. Исход определяется **профилем компании** (синтетические ответы моков привязаны к ИНН) и **суммой заявки**.

| Учётка (README) | Компания | Что ввести | Исход |
| --- | --- | --- | --- |
| client-ip-good | ИП, хорошие обороты, чистая КИ | любая сумма ≤ лимита | Авто-одобрение → подписать → «Выдано» |
| client-ooo-load | ООО, высокая нагрузка | сумма выше расчётного лимита | Встречное (меньше сумма или длиннее срок) |
| client-ooo-gap | ООО, расхождение выручки с оборотами | любая | Дозапрос → клиент дополняет → решение |
| client-ip-bad | ИП, просрочки в КИ или налоговый долг | любая | Отказ с клиентской причиной и действием |
| client-ooo-border | ООО, пограничный скор | любая | «У специалиста» → войти как `underwriter` → решение |
| underwriter | сотрудник банка | — | очередь, карточка, журнал |

README ведёт по шагам; пограничную ветку жюри доводит само через вход андеррайтера. Точные пороги — этап 3.

## 7. Блок T — отдельный бюджет (~25–30% мощности)

Docker и сиды (с 24.10), README, OpenAPI и коллекция запросов (из контрактов), диаграмма состояний и модель данных (из этапа 3), THIRD_PARTY_NOTICES, автотесты на четыре исхода и недопустимые переходы, репетиция T20. Отвечает назначенный человек и агент (этап 4).

## 8. Польза и издержки для клиента и банка (F21, критерий 6)

| | Клиент | Банк |
| --- | --- | --- |
| Польза | Профиль уже заполнен; видит, где заявка и что делать; понимает отказ или встречное и что изменить | Автомат решает типовые заявки (меньше стоимость и time-to-yes); человек только для исключений; меньше повторных бесполезных заявок; встречное вместо отказа — сохранённая выдача |
| Издержки и риски | Нужно дать согласия; ИП может возразить (дольше) | Объяснение причин требует дисциплины (слой политики, снимок решения); ручная очередь — SLA на андеррайтера; риск «обучить обходу» — снимаем категориями без порогов |

## 9. Решение (2026-10-23, D5)

**Строим B-lite, контракты закладываем под B.** Цель — B. Три продукта: экспресс-кредит, оборотный кредит, овердрафт. Поручитель — в той же сессии.

### Путь B-lite → B: две независимые надстройки
| Надстройка | Задел в этапе 3 (делаем сразу) | Что добавить для B | Ворота включения |
| --- | --- | --- | --- |
| Б1. Поручитель отдельной учёткой | Поручитель — отдельный участник заявки (`party`) со своими согласиями, подписью и статусом «ожидает поручителя». В B-lite его заполняет та же сессия | Учётка `guarantor`, экран «Входящие на подпись», ожидание в ленте статуса | Ядро B-lite проходит E2E в Docker |
| Б2. Предрасчёт «узнать доступную сумму» | Скоринг и политика — чистые функции; режим `preview` без основной части КИ (информационная часть — без согласия, LB) зарезервирован в контракте | Экран предрасчёта до заявки, перенос расчёта в заявку | То же + Б1 не горит |

**Правило:** надстройку берём, только если ядро B-lite уже проходит все E2E-сценарии в Docker. Не позже точки контроля 25.10 в 20:00. После неё новых надстроек нет, только стабилизация.

**Обратный путь B → B-lite** дешёвый, только если начинаем с B-lite. Если начать сразу с B и резать, часть работы уйдёт в корзину. Поэтому порядок такой: ядро → андеррайтер → Б1 → Б2.
