# Модель принятия кредитного решения

Детерминированные правила. ML и LLM нет (D5). Конвейер: **стоп-факторы → скоринг (оценка риска) → кредитная политика продукта (условия) → маршрутизация**. Скоринг отделён от политики: одна и та же оценка даёт разные условия для разных продуктов (кейс с. 14, F11).
Все пороги и веса — в конфигурации (`decision_config`, версия хранится в каждом решении), а не в коде. Цифры ниже — стартовые [Д], калибровка на синтетике.

## 2. Проверка данных (до сбора сведений) → дозапрос

| Код | Правило | Что просим у клиента |
| --- | --- | --- |
| `VAL_REVENUE_MISMATCH` | \|`declared_revenue_year` − 12 × `avg_turnover`\| / (12 × `avg_turnover`) > 40% | Подтвердить выручку или пояснить разницу (часть выручки идёт на счета в других банках) |
| `VAL_PURPOSE_UNCLEAR` | цель «Другое» без описания | Описать цель |
| `VAL_REQUIRED` | нет обязательного поля | Заполнить поле (на практике ловит форма, правило — для API) |

Пункты дозапроса и их коды — `contracts/codes.md`. Ответ клиента **закрывает** правило на этой заявке (повторно не срабатывает). Для скоринга берутся обороты по счёту; заявленная выручка — только для сверки.

## 3. Стоп-факторы → отказ

| Код | Условие | Клиентская категория | Текст и действие для клиента |
| --- | --- | --- | --- |
| `SF_INACTIVE` | компания не действует | Данные о компании | «По данным реестра компания не действует» — проверьте сведения в ЕГРЮЛ/ЕГРИП |
| `SF_BANKRUPTCY` | процедура банкротства | Финансовое положение | «Есть сведения о процедуре банкротства» |
| `SF_AGE` | `business_age_months` < 6 | Срок ведения бизнеса | «Бизнесу меньше 6 месяцев» — подайте заявку после {дата} |
| `SF_OVERDUE` | `current_overdue` > 0 или `max_dpd_12m` > 60 | Кредитная история | «Есть просроченная задолженность» — погасите её; повторно через 30 дней |
| `SF_TAX_DEBT` | `tax_debt` > 50 000 ₽ или `enforcement_sum` > 100 000 ₽ | Налоги и обязательства | «Есть задолженность перед бюджетом или по исполнительным листам» — погасите и подайте снова |
| `SF_OKVED` | ОКВЭД в стоп-листе (азартные игры, финансовое посредничество) | Условия продукта | «Вид деятельности не подходит для этого продукта» |

**PTR** = (`existing_payments_month` + платёж по новому кредиту) / `avg_turnover`. Платёж для скоринга считается по **консервативной ставке = КС + максимальный спред продукта (оценка C)**, поэтому скоринг не зависит от оценки и круга нет. Для овердрафта платёж = 10% лимита.

**Оценка (grade):** A ≥ 75; B 60–74; C 45–59 (пограничная → андеррайтер); D < 45 → отказ `LOW_SCORE` («Финансовые показатели»; действие: «попробуйте меньшую сумму или овердрафт»).
Каждый фактор пишет в решение строку `{фактор, значение, баллы}` — это и есть объяснение (Q37).

## 5. Кредитная политика продуктов

Ставка = **ключевая ставка (параметр с датой) + спред по оценке**. Скидки за поручительство в MVP нет: для ООО поручитель обязателен, скидка ничего не различает (параметр конфигурации на будущее). При КС 14% базовые ставки 21–28% — в диапазоне Альфы и Сбера (market.md).

| | Экспресс-кредит | Оборотный кредит | Овердрафт |
| --- | --- | --- | --- |
| Цель | любые цели бизнеса | пополнение оборотных средств | кассовые разрывы |
| Сумма | 300 тыс. – 5 млн | 500 тыс. – 15 млн | лимит 100 тыс. – 5 млн |
| Срок | 6–36 мес. | 3–24 мес. | 12 мес., транш до 60 дней |
| Лимит по оборотам | ≤ 2 × `avg_turnover` | ≤ 3 × `avg_turnover` | ≤ 40% × `avg_turnover` |
| Ограничение нагрузки | PTR ≤ 30% | PTR ≤ 30% | — (лимит по оборотам) |
| Порог авто-решения | ≤ 3 млн | ≤ 5 млн | весь диапазон |
| Спред A / B / C | +8 / +10 / +12 п.п. | +7 / +9 / +11 п.п. | +10 / +12 / +14 п.п. |
| Поручитель | ООО — учредитель с долей >50%; ИП — при сумме > 3 млн | так же | ООО — учредитель |

Платёж — аннуитет по ставке оферты (КС + спред по оценке), округление до рубля ROUND_HALF_UP; деньги — целые рубли. **Овердрафт — упрощённо:** без аннуитета и графика; лимит = min(запрошенный, 40% × `avg_turnover`); встречное — только уменьшение лимита; нагрузка PTR в политике не проверяется; выдача = открытие лимита.

## 6. Встречное предложение (кредиты, не овердрафт)

Обозначения: `free` = 30% × `avg_turnover` − `existing_payments_month` (сколько можно платить в месяц), `cap` = лимит по оборотам, ставка — по оценке. **Оценка на сумме встречного не пересчитывается**: встречное — это решение политики при той же оценке.
1. `free` ≤ 0 → отказ `HIGH_LOAD`.
2. Запрошенная сумма ≤ `cap` и платёж на запрошенный срок ≤ `free` → **одобрение** как просили.
3. Иначе перебираем срок от запрошенного +1 до максимума продукта: первый срок, где сумма ≤ `cap` и платёж ≤ `free` → **встречное: больший срок, та же сумма**.
4. Иначе сумма = min(`cap`, сумма с платежом `free` на **максимальном** сроке), округление вниз до 50 тыс.; если ≥ минимума продукта → **встречное: меньшая сумма на максимальный срок**.
5. Иначе → отказ `HIGH_LOAD` («Долговая нагрузка»; действие: «рассмотрите овердрафт или подайте позже»).

Встречное — новая версия оферты (`offer.version`), прежняя сохраняется.

## 6a. Порядок применения правил (детерминированный)
1. Стоп-факторы по порядку таблицы §3 — первый сработавший определяет причину.
2. Скоринг → оценка. D → `LOW_SCORE`.
3. Политика продукта (§5–6) → одобрение / встречное / `HIGH_LOAD`.
4. Маршрутизация (§7) применяется **к любому итогу шагов 1–3**: если хоть одно условие ручного рассмотрения истинно, итог становится рекомендацией андеррайтеру, а не решением. Приоритет `route_reason`: `NO_AUTO_CONSENT` > `GRADE_C` > `AMOUNT_ABOVE_AUTO`. Стоп-факторы и отказы у ООО и у ИП с согласием — авто-отказ без андеррайтера; у ИП без согласия на авто-решение — к андеррайтеру с рекомендацией «отказ». `AMOUNT_ABOVE_AUTO` применяется только к одобрению и встречному. Возраст бизнеса считается на дату подачи заявки (`submitted_at`). Эталон — функция `decide()` в `contracts/decision_reference.py`.

## 7. Маршрутизация

Авто-решение (A/B, сумма ≤ порога, у ИП есть согласие на авто-решение) → оферта. Иначе — андеррайтер с **рекомендацией системы** (решение, которое принял бы автомат) и всеми факторами. Андеррайтер может согласиться или отклониться, комментарий обязателен. Расхождения с рекомендацией попадают в журнал (метрика качества модели).

## 7a. Обоснованность решения: протокол и «что изменило бы решение»

Каждое решение (`decision`) хранит и показывает андеррайтеру **протокол** (`DecisionBank` в `contracts/api-types.ts`):
1. **Входы со снимком:** значения всех признаков, источник и время получения (ЕГРЮЛ, БКИ, ФНС, обороты банка).
2. **Сработавшие правила** (`rules_fired`): код, значение, порог, эффект. Пример: `SF_OVERDUE`: просрочка 35 000 ₽ > 0 → стоп.
3. **Разбор баллов** (`factors`): признак, значение, баллы из максимума, правило.
4. **Расчёт политики** (`policy`): ставка, средний оборот, текущие платежи, свободный платёж, лимит по оборотам, максимум суммы, ход расчёта встречного по шагам.
5. **«Что изменило бы решение»** (`what_if`): ближайшие условия, при которых исход стал бы лучше («одобрение при сумме ≤ 1 450 000 ₽»; «оценка B при отсутствии налогового долга»). Считается перебором той же политики. Клиент видит это в виде действия («рассмотрите сумму до 1 450 000 ₽»), андеррайтер — полностью.
6. **Версия конфигурации и ключевая ставка** на момент решения: решение воспроизводимо.
7. **Ручное решение:** кто, когда, комментарий; если отличается от рекомендации — событие `UNDERWRITER_OVERRIDE`.

Андеррайтер видит **все точные причины**, включая внутренние (ПОД/ФТ, антифрод) — ограничение только для клиента. Протокол открывается в карточке андеррайтера и печатается (страница «Протокол решения» — версия для печати средствами браузера).
