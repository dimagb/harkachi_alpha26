## 3. Как координируемся — варианты

### A. GitHub как шина + Telegram для людей (рекомендую)
- Задачи — GitHub Issues с меткой роли (`backend`, `frontend`, `analytics`) и ссылкой на пункт `TASKS.md`. Агент сам берёт свои: `gh issue list --label backend --state open`.
- Узкий вопрос по контракту агент пишет комментарием в issue с меткой `question`. Тимлид отвечает в контрольные точки; срочное человек пересылает в Telegram.
- Работа идёт через короткие ветки `<роль>/<задача>` и PR в `main`. CI на каждый PR: линтер, тесты, сборка Docker. Слияние только при зелёном CI.
- Ревью: обычные PR — встроенное ревью Codex и `/code-review` от меня. PR, которые трогают деньги, переходы состояний, права доступа или контракты, проверяет субагент `reviewer`. Владельцы папок — в `CODEOWNERS`.
- Telegram — обычная группа людей без бота. Три контрольные точки в день (например, 11:00, 16:00, 21:00): каждый оператор вставляет отчёт своего агента в формате «сделано / дальше / блокер».
- **Плюсы:** никакой новой инфраструктуры. История видна жюри (кейс: репозиторий с историей). Тимлид не просыпается на каждое сообщение, а лимит Claude тратится только в контрольные точки.
- **Минусы:** человек передаёт срочное руками. Ответ на вопрос может ждать до ближайшей контрольной точки (не больше 5 часов).
- **Смягчение:**
  - агент не простаивает: выбирает консервативное толкование контракта, пишет его в PR как допущение и берёт следующую задачу;
  - блокирующий вопрос оператор пишет в Telegram, человек передаёт его тимлиду в сессию — ответ за минуты;
  - уведомления GitHub о метке `question` можно направить в Telegram (бот GitHub), тогда человек увидит вопрос сразу.

### B. Шина Telegram из заготовки (`drafts/telegram-bus/`)
- Хаб на VPS, у каждого агента бот, хуки в Claude Code и Codex. Агенты сами получают адресные сообщения посреди работы, есть дежурный режим, на доске видно, кто что делает.
- **Плюсы:** быстрые узкие ответы без участия человека. Заготовка готова и проверена 44 тестами.
- **Минусы:**
  - настройка займёт 1,5–2 ч: BotFather, группа с темами, токены, `.agentbus.env` и доверие к хукам на трёх чужих ноутбуках у операторов-непрограммистов;
  - хаб — ещё одна точка отказа;
  - **хук тимлида будит меня на каждое адресное сообщение**, а это прямой расход самого дефицитного ресурса;
  - дежурный режим держит сессии Codex включёнными и тратит их лимит;
  - в заготовке другие роли (`ml`, `ops`), её нужно перенастроить.

### C. Готовая методика (`github/spec-kit`, BMAD-METHOD)
- Своя цепочка «спецификация → план → задачи» и свои роли.
- **Минусы:** спецификацию и контракты мы уже сделали своими силами. Перекладывать их в чужой формат — день работы без пользы для оценки. **Отвергаю.**

**Рекомендация: A.** Моё мнение изменится, если в первый день разработки вопросы агентов будут застревать дольше половины дня. Тогда включаем B в упрощённом виде (хаб без дежурного режима, тимлид без хука). Варианты A и B совместимы: задачи и PR в любом случае живут в GitHub.

## 5. Риски методики и ответы
- **Codex отступает от контракта.** Pydantic с `extra="forbid"`, TS-клиент из `openapi.json`, golden-тесты в CI — расхождение сразу видно как красный CI.
- **Два агента правят один файл.** Владение папками через `CODEOWNERS`. Общие файлы (`docker-compose.yml`, `contracts/`) правит только тимлид.
- **Катя пропадает.** Её задачи не блокируют других: у бэкенда есть фейк-адаптер, README дописывает тимлид 26.10. Задачи нарезаны по 1–2 часа, и каждая полезна сама по себе.
- **Кончается лимит Claude.** Ревью рутинных PR выполняет Codex, у меня — только рискованные. Тимлид работает в контрольные точки. При <20% недели остаются только сдача и чек-лист.
- **Операторы не справляются с git.** В `AGENTS.md` есть готовый порядок работы для агента: ветка, коммит, `gh pr create`, исправление CI. Оператору нужно только подтверждать команды.

## 6. Скиллы и MCP для Codex (Plus: окно 5 ч + недельный лимит)
Ставим одинаковый набор, который выбрал тимлид. Сами участники ничего не ищут: случайный скилл из интернета означает риск чужого кода и лишний расход лимита на его описание в контексте.

| Что | Кому | Зачем |
| --- | --- | --- |
| MCP `context7` | всем | Актуальная документация (Mantine 9, FastAPI): меньше кода по устаревшей памяти |
| Скиллы из `superpowers`: только `test-driven-development`, `systematic-debugging`, `verification-before-completion` (папками, без `using-superpowers`) | всем | Тесты до кода и проверка перед «готово». Без вводного скилла, который заставляет вызывать скиллы на каждый шаг и тратит лимит |
| `gh-fix-ci`, `gh-address-comments` (openai/skills) | всем | Оператор-непрограммист говорит «почини CI» или «исправь замечания ревью» |
| MCP `playwright` | фронтенд, аналитика | Посмотреть экран; e2e демо-пути |
| `frontend-design` | фронтенд | Дизайн-дисциплина поверх токенов человека |
| Не ставим: shadcn, hf-cli, vercel-labs/agent-skills, trailofbits | — | Не наш стек или не на этом этапе (trailofbits запустит тимлид на этапе 6) |

Скиллы кладём в репозиторий (`.agents/skills/`), чтобы у всех был одинаковый набор. Личная настройка — только MCP (`codex mcp add …`). Инструкцию по установке тимлид пишет в `docs/team/codex-setup.md` после ворот 4.
