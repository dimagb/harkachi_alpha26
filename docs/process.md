# Модель кредитного процесса (этап 3)

Основа: `research.md` (D4), `mvp.md` (D5: B-lite с заделом под B), `legal/legal-basis.md`. Статусы и переходы — `state-machine.md`. Скоринг и политика — `decision-model.md`.

## 1. Границы

- **Начало:** действующий клиент банка (ИП или ООО) вошёл в кабинет с потребностью в финансировании.
- **Конец:** «Выдано» (смоделированное зачисление + событие отчёта в БКИ) **или** отказ / отзыв / истечение.
- **Вне границ:** регистрация бизнеса, открытие счёта, залог и оценка, кредитный комитет, обслуживание после выдачи, реальные подписи и деньги (допущения — `assumptions.md`).

## 2. Участники

| Участник | Кто | Что делает | В прототипе |
| --- | --- | --- | --- |
| Заявитель | Бухгалтер, финдиректор или директор | Готовит заявку, отвечает на дозапросы | Роль клиента; право подписи — по флагу |
| Подписант | Директор (ЕИО) ООО или сам ИП | Даёт согласия, подписывает оферту | Тот же пользователь, если у него `can_sign` |
| Поручитель | Учредитель-физлицо с долей >50% (ООО) | Согласие на ПДн и БКИ, подписывает поручительство | B-lite: в той же сессии (директор = учредитель). B (Б1): своя учётка |
| Кредитный конвейер | Система | Проверки, обогащение, скоринг, политика, маршрутизация, выдача | Фоновый обработчик (worker) |
| Андеррайтер | Сотрудник банка | Рассматривает исключения и возражения, решает с комментарием | Роль банка в том же интерфейсе |
| Внешние источники | БКИ, ЕГРЮЛ/ЕГРИП, ФНС («Прозрачный бизнес»: налоговый долг, ФССП, банкротство) | Отдают сведения по ИНН | Мок-сервис с синтетикой |
| Внутренние данные банка | Профиль клиента, обороты по счёту, флаги ПОД/ФТ | Источник данных для скоринга | Синтетика в БД банка |

## 3. Этапы

| # | Этап (для клиента) | Что происходит | Кто | Данные на входе → выходе | Исходы |
| --- | --- | --- | --- | --- | --- |
| 1 | Заявка | Выбор цели и продукта; форма заявки, профиль подставлен из ЕГРЮЛ/ЕГРИП-мока и профиля банка; калькулятор платежа | Клиент | Профиль → `application` (продукт, сумма, срок, цель, заявленная выручка) | Черновик сохраняется на каждом шаге |
| 2 | Согласия и отправка | Согласия: ПДн (заёмщик-ИП, подписант, поручитель), основная часть КИ в БКИ, авто-решение (ИП). Подпись кодом | Подписант | → `consent` × N, `signature` | Подана. Без согласия на БКИ отправка невозможна |
| 3 | Проверка данных | Полнота и формат, нормализация (ИНН, суммы, даты); сверка заявленной выручки с оборотами | Конвейер | `application` → нормализованная заявка | Дальше / **дозапрос** |
| 3a | Дозапрос | Клиент уточняет данные в той же заявке; срок ответа | Клиент | Комментарий + исправленные поля | Обратно на проверку / истечение / отзыв |
| 4 | Сбор сведений | Запросы в БКИ (основная часть — по согласию), ЕГРЮЛ/ЕГРИП, ФНС; повтор при сбое | Конвейер | ИНН → `bureau_report`, `registry_record`, `tax_check` | Дальше / ручной разбор (источник недоступен) |
| 5 | Оценка | Стоп-факторы → балльный скоринг → кредитная политика продукта → маршрутизация | Конвейер | Всё выше → `decision` (снимок входов, скор, правила, коды причин) | Одобрение / встречное / отказ / к андеррайтеру |
| 5a | Рассмотрение специалистом | Пограничный скор, сумма выше порога авто-решения, сбой источника, возражение ИП. Андеррайтер видит данные, факторы и рекомендацию системы | Андеррайтер | `decision` → ручное решение с комментарием | Одобрение / встречное / отказ / дозапрос |
| 6 | Решение | Клиент видит результат и **клиентскую** причину (категория + что делать); банк видит полный журнал | Клиент | `offer` (версия) / `client_reason` | Принять / отказаться; отказ ИП при авто-решении → «Не согласен» |
| 7 | Подписание | Подпись оферты подписантом; для ООО — согласие и подпись поручителя | Подписант, поручитель | `offer` → `contract`, `signature` | Подписано / истечение |
| 8 | Выдача | Предпроверка (оферта и согласие на БКИ действуют), смоделированное зачисление, график платежей, событие `BKI_REPORT` | Конвейер | `contract` → `disbursement` | Выдано |

## 4. Где автомат, где человек (Q10)

- **Автомат:** проверка данных, сбор сведений, стоп-факторы, скоринг, политика; авто-решение для оценок A и B в пределах порога суммы продукта; выдача.
- **Человек (андеррайтер):** оценка C (пограничная); сумма выше порога авто-решения продукта; источник недоступен после повторов; возражение ИП против авто-решения (152-ФЗ ст. 16); ИП не дал согласия на авто-решение.
- **Почему:** типовые заявки банк решает быстро и дёшево, человек нужен там, где модель не уверена или закон даёт право на пересмотр (`research.md` §3, банк).

## 5. Причины решения — два уровня (legal F82–F94)

- `internal_reason`: полный код правила, значения факторов, пороги — видит только банк.
- `client_reason`: категория + понятный текст + действие. ПОД/ФТ, СБ и антифрод клиенту не показываются: используется нейтральный `ADDITIONAL_CHECKS` («заявка не прошла дополнительные проверки банка»). Подменять причину нельзя.
- Отказ в кредите — `CREDIT_DECLINE`, не AML-отказ. На 115-ФЗ в кредитном отказе не ссылаемся.

## 6. Особые случаи

| Случай | Поведение |
| --- | --- |
| Отзыв заявки клиентом | Возможен до подписания договора → «Отозвана» |
| Отказ клиента от встречного предложения | → «Отозвана» с причиной `CLIENT_REJECTED_OFFER` |
| Нет ответа на дозапрос | Через N дней (демо: настраивается) → «Истекла» |
| Оферта не принята | Срок оферты 30 дней (как «Кредитный потенциал» у Сбера) → «Истекла» |
| Согласие на БКИ истекло к выдаче | Повторное согласие перед выдачей (1 год для МСП; в демо проверка есть, истечение воспроизводится тестом) |
| Сбой мок-сервиса | 3 повтора с паузой → к андеррайтеру с причиной `SOURCE_UNAVAILABLE` |
| Повторная подача после отказа | Новая заявка со ссылкой на прежнюю; при отказе по стоп-фактору — не раньше даты из `client_reason` (политика: 30 дней) |
| Возражение ИП | В течение 30 дней после авто-отказа → к андеррайтеру; ответ — в карточке заявки |
| Нет права подписи | Пользователь без `can_sign` готовит и отправляет на подпись, но не подписывает |
