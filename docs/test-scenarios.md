# Сценарии проверки кредитного кабинета

Документ задаёт ожидаемое поведение для проверки прототипа: сценарии S-01…S-23 с входами, шагами и ожидаемыми результатами. Они автоматизированы и прогоняются на стенде: сквозные тесты API (`tests/e2e/api`, 268 тестов), тесты демо-пути в интерфейсе (`frontend/e2e`, Playwright), эталонные расчёты решения (`contracts/decision_reference.py`, golden-тесты бэкенда); ручные шаги — `docs/notes/stand-checklist.md`. Результаты — README, раздел «Как мы проверяли».

Источники: [функциональные требования](requirements-checklist.md), блок с ID `F…`; [машина состояний](state-machine.md), таблица переходов; [персонажи](../contracts/personas.json), данные `demo`; [реестр кодов](../contracts/codes.md). В чек-листе функциональный блок озаглавлен «A. Функциональные», а в карточке A-04 назван «блок F»: здесь покрываются именно все его F-пункты. Пункта F17 в источнике нет.

## Подготовка и правила прогона

- Использовать локальный стенд с загруженными демо-персонажами, работающими worker, планировщиком и моками. Обычные сценарии выполняются без `MOCK_FAILURE_INN`; S-15 требует отдельного запуска.
- Входить под логином из таблицы; пароль — настроенный `DEMO_PASSWORD`, как указано в метаданных `personas.json`. Пароль в документ не переносится. Для банка использовать отдельную сессию `underwriter` (роль `UNDERWRITER`). Логины и право подписи сверены с `users`/`staff` того же файла; иных персональных данных для сценариев не требуется.
- «Подать `<персонаж>`» означает: войти, создать новый черновик из `demo.app` этого персонажа, проверить подстановку профиля, задать согласия точно из `demo.consents`, подписать обязательные согласия действующим кодом из интерфейса и отправить заявку. В частности, `auto_decision=false` не подменять на `true`. Деньги, срок, цель и выручку брать из полей исходного JSON, а не из чисел, придуманных для теста.
- Каждый независимый сценарий начинает новую заявку; продолжения явно ссылаются на предыдущий сценарий. У разных прогонов свои ID и версии оферт. Для повторения отрицательного шага сохранять состояние до него, не применять прямую правку БД.
- В UI выбирать действие по смыслу («Подать заявку», «Принять предложение» и т. п.); названия здесь не обязаны буквально совпадать с надписью кнопки. Вызовы `POST /…` приведены относительно API и взяты из таблицы переходов. Формат запросов брать из действующего контракта API, не достраивать поля по этому документу.
- Ожидать системные шаги опросом состояния до результата с ограничением времени прогона; не считать фиксированную паузу доказательством завершения. Быстрые промежуточные состояния проверять также по журналу событий. Каждый переход должен оставлять автора, время, исходное и новое состояние, причину.
- Клиент видит понятные русские объяснения, доступные действия и следующий шаг. Технические коды в ожидаемых результатах предназначены для проверки API и банка. Оценку, факторы, правила и внутренние причины проверять в банковской сессии, не требовать их показа клиенту.
- Колонка «Автоматизация» показывает, чем проверяется сценарий: golden — эталонный расчёт решения в тестах бэкенда; API — сквозные тесты `tests/e2e/api`; UI — тесты демо-пути `frontend/e2e` (Playwright); «вручную» — чек-лист `docs/notes/stand-checklist.md`.

## Что фиксировать при выполнении

Для каждого прогона записать ID сценария, версию проекта, конфигурацию (обычная / сбой источника / сдвиг времени), учётку, ID заявки, фактические состояния и результат «пройден / не пройден». Для ошибки приложить обезличенный ответ API с HTTP-статусом; для переходов — события; для UI — наблюдение или снимок экрана. Не сохранять токены, пароли и OTP в отчёте.

Отчёты о прогонах: `docs/audit/state-coverage.md` (все 31 переход автомата), `docs/audit/demo-path.md` (демо-путь в интерфейсе), `docs/audit/ui.md` (автообход экранов), `docs/demo/rehearsal-T20.md` (запуск и сценарии строго по README).
